# Граф зависимостей Alpine Linux: вариант 1

Практическая работа по конфигурационному управлению. Язык: Python.
Реализованы этапы 1-4: проверка YAML-настроек, получение прямых
зависимостей и построение графа итеративным DFS с ограничением глубины.
Поддерживаются реальные репозитории Alpine, локальные учебные графы
и порядок загрузки, в котором зависимости предшествуют своим пользователям.
Для чтения YAML используется PyYAML. Библиотеки получения зависимостей
пакетов не используются.

## Запуск в PyCharm

1. Откройте эту папку через File → Open.
2. Выберите интерпретатор Python 3.10 или новее, желательно с `.venv`.
3. Откройте Terminal внизу PyCharm.
4. Установите зависимость: `py -m pip install -r requirements.txt`.
5. Запустите: `py -m src.main`.

Запускайте команды из корня проекта, где лежит `config.yaml`.
Для запуска кнопкой Run создайте Python-конфигурацию: Module name =
`src.main`, Working directory = корень проекта.
В Windows также можно выполнить `run.bat`.
Команды приведены для Windows с Python Launcher (`py`). На других
системах или в активном виртуальном окружении используйте `python`.
Сборка не требуется.

## Настройки

| Ключ | Значение |
| --- | --- |
| package_name | Непустое имя пакета: буквы, цифры, `+`, `_`, `.`, `-` |
| repository | HTTP(S)-адрес или путь к существующему тестовому файлу |
| test_mode | `true` для тестового файла, иначе `false`, без кавычек |
| package_version | Непустая строка версии, обязательно в кавычках |
| max_depth | Целое число от 0; 0 означает только исходный пакет |

В тестовом режиме относительный путь считается от папки YAML-файла.
В режиме `--show-config` проверяется существование тестового файла,
но его содержимое ещё не читается. При обычном запуске тестовый файл
читается как YAML-словарь вида `A: [B, C]`. Имена состоят из больших
латинских букв, каждый упомянутый пакет должен быть описан отдельным ключом.
Тестовый граф не содержит версий: `package_version` остаётся обязательной
настройкой, но в этом режиме не участвует в выборе узлов.
Для режима `--direct` нужен `test_mode: false`; глубина в нём не применяется.

Другой файл настроек:

```console
py -m src.main --config examples/config-test.yaml
```

Пример вывода стандартного запуска (`py -m src.main`):

```text
Граф зависимостей (максимальная глубина: 3):
  busybox@1.36.1-r31 -> musl@1.2.5-r4
  musl@1.2.5-r4 -> нет зависимостей
Всего пакетов: 2
Циклы в построенном графе:
  не обнаружены
```

Пример проверен на реальном индексе Alpine v3.20 main x86_64.
Репозиторий может обновляться. Если выбранной версии больше нет,
программа сообщит об этом и покажет доступные версии; автоматически
подменять выбранную версию другой программа не будет.

Чтобы повторить первый этап без доступа к сети:

```console
py -m src.main --show-config
```

Его вывод:

```text
package_name: busybox
repository: https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64/
test_mode: false
package_version: 1.36.1-r31
max_depth: 3
```

## Как работает второй этап

Для повторения второго этапа используйте:

```console
py -m src.main --direct
```

Пример его вывода:

```text
Пакет: busybox
Версия: 1.36.1-r31
Прямые зависимости:
  so:libc.musl-x86_64.so.1
```

1. К URL каталога репозитория добавляется `APKINDEX.tar.gz`.
   Также можно указать прямой URL этого архива.
2. Архив скачивается через `urllib.request` с тайм-аутом 30 секунд.
3. `tarfile` читает файл `APKINDEX` в памяти, без распаковки на диск.
4. Наш код разбирает записи: `P` - имя, `V` - версия, `D` - зависимости.
5. Выбирается точное совпадение имени и версии и выводятся зависимости.

Ограничения версий (`lib>=2`) и виртуальные имена (`so:libc.so.1`)
выводятся в исходном виде. Записи с `!` обозначают конфликты,
поэтому в список зависимостей не включаются. В режиме построения графа
виртуальные зависимости сопоставляются пакетам по полю `p` (provides).

Формат индекса описан в
[документации Alpine](https://wiki.alpinelinux.org/wiki/Apk_spec#APKINDEX_Format).
Для получения зависимостей используются только стандартные модули Python;
менеджер `apk` и готовые библиотеки анализа зависимостей не вызываются.

## Как работает третий этап

Обход использует стек, а не рекурсивные вызовы. Корень имеет глубину 0,
прямые зависимости - 1 и так далее. Узлы на границе глубины присутствуют
в результате, но их зависимости не читаются. Отметка `[граница глубины]`
не означает, что у пакета нет зависимостей: его содержимое не анализировали.

Для общих зависимостей хранится минимальная найденная глубина. Если DFS
сначала дошёл до узла длинным путём, а затем коротким, его потомки
повторно обходятся с увеличившимся остатком глубины. Метаданные узла
при этом берутся из кэша. Повторные рёбра удаляются.

Циклы обнаруживаются отдельным итеративным DFS по уже построенному графу:
обратное ребро в активный путь образует цикл. Общий потомок двух ветвей
циклом не считается. Выводятся циклы, соответствующие найденным обратным
рёбрам, а не все возможные простые циклы. Циклы за границей глубины
обнаружить нельзя. Наличие цикла не прерывает построение графа.

В режиме Alpine индекс скачивается один раз. Узлы подписаны как
`имя@версия`. Поставщик `so:...`, `cmd:...` или другого виртуального имени
находится по `provides`. Проверяются ограничения `=`, `<`, `>`, `<=`, `>=`,
`~`, `=~`, `~=`, `<~`, `>~`; числовые компоненты, суффиксы и ревизии
версий сравниваются нашим кодом. При ограничении виртуальной зависимости
используется версия из `provides`, а не версия самого пакета.

Правила выбора: сначала собственное имя пакета, затем максимальный
`provider_priority` (`k`), затем наибольшая подходящая версия одного
поставщика. Если остаются разные имена пакетов, выводится ошибка
неоднозначности. Версия стартового пакета закреплена конфигурацией.
Отсутствующая зависимость вызывает ошибку, а не становится фиктивным листом.

Это анализ одного заданного репозитория, без полного решателя установки:
не учитываются состояние установленной системы, теги репозиториев,
межпакетные конфликты и совместимость всех выбранных версий между собой.
В разных ветвях могут присутствовать разные версии одной зависимости;
в графе они имеют разные метки. При неизвестном формате версии или
операторе выводится ошибка.

Описание версий и виртуальных имён:
[APKBUILD Reference](https://wiki.alpinelinux.org/wiki/APKBUILD_Reference).

### Демонстрация на учебных графах

Каждую команду выполните из корня проекта. Интернет не требуется,
основной `config.yaml` менять не нужно.

| Конфигурация | Случай и результат |
| --- | --- |
| `examples/config-test.yaml` | Ромб: A ведёт в B и C, обе ветви в D; 4 узла, циклов нет |
| `examples/config-cycle.yaml` | Цикл A → B → C → A; обход завершается, цикл выводится |
| `examples/config-depth.yaml` | Длинный и короткий пути к D; E и F не теряются |
| `examples/config-zero.yaml` | Глубина 0: только A с отметкой границы |
| `examples/config-empty.yaml` | Один пакет A без зависимостей |

Пример запуска циклического графа:

```console
py -m src.main --config examples/config-cycle.yaml
```

```text
Граф зависимостей (максимальная глубина: 3):
  A -> B
  B -> C
  C -> A, D
  D [граница глубины]
Всего пакетов: 4
Циклы в построенном графе:
  A -> B -> C -> A
```

Для остальных примеров замените путь после `--config` на путь из таблицы.

## Четвёртый этап: порядок загрузки

```console
py -m src.main --order
```

Для текущего примера busybox выводится:

```text
Порядок загрузки (зависимости раньше пакета):
  1. musl@1.2.5-r4
  2. busybox@1.36.1-r31
```

Порядок вычисляется алгоритмом Кана без рекурсии. Для каждого узла
считается количество зависимостей, ещё не попавших в результат.
Сначала выбираются узлы с нулевым счётчиком. После добавления зависимости
уменьшаются счётчики использующих её пакетов. Из нескольких готовых узлов
выбирается лексикографически первый. Результат воспроизводим, каждый пакет
встречается один раз. Это допустимый порядок зависимостей, а не полный
план установки, учитывающий состояние системы и конфликты.

При цикле строгий порядок невозможен: программа выводит путь цикла,
возвращает код 1 и не печатает частичный успешный список.
Если достигнута граница `max_depth`, порядок строится для полученной части
графа с явным предупреждением. За границей могут находиться другие
зависимости и циклы; такой результат не является полным планом загрузки.

### Проверка на учебных графах

```console
py -m src.main --order --config examples/config-test.yaml
py -m src.main --order --config examples/config-cycle.yaml
py -m src.main --order --config examples/config-depth.yaml
py -m src.main --order --config examples/config-empty.yaml
py -m src.main --order --config examples/config-zero.yaml
```

| Случай | Результат |
| --- | --- |
| Ромб | D, B, C, A; общая зависимость D выводится один раз |
| Цикл | Ошибка с путём A → B → C → A, код завершения 1 |
| Глубина 3 | F, E, D, C, B, A; предупреждение о границе глубины |
| Пакет без зависимостей | Только A, без предупреждения |
| Глубина 0 | Только A, с предупреждением о частичном графе |

### Сравнение с менеджером apk

Отдельный проверочный инструмент запускается в Linux с Docker:

```console
python -m tools.compare_apk
```

Он проверяет busybox, zlib и curl из Alpine v3.20 main x86_64.
Наш граф строится с глубиной 100. В контейнере `alpine:3.20` создаётся
пустой временный корень, обновляется индекс и выполняется
`apk add --simulate` с точной версией пакета. Установка не выполняется.
Пустой корень нужен, чтобы уже установленные в контейнере пакеты
не пропали из сравниваемого плана.

Сравниваются наборы пакетов, конкретные последовательности и положение
каждой зависимости относительно использующего её пакета. Разные
последовательности независимых ветвей допустимы: наша программа выбирает
готовый пакет по алфавиту, а apk использует порядок своей транзакции.
Необъяснённое различие набора пакетов или нарушение зависимости считается
ошибкой проверки. Дополнения apk принимаются только если в их метаданных
есть `install_if`, все его условия выполнены пакетами нашего графа,
а собственные зависимости дополнений уже присутствуют и идут раньше них.
В отчёте явно указывается, что наборы различаются, и приводятся условия.
Другие различия требуют разбора: возможны обновления индекса между запросами,
различия поставщиков или логики решателя. Сырые результаты apk остаются
в логе проверки, чтобы вывод можно было перепроверить.

Сравнение запускается автоматически после отправки в `main`:
[GitHub Actions](https://github.com/eemp7y/apk-dependency-graph/actions).
Менеджер apk используется только отдельным инструментом сравнения,
приложение не получает через него информацию о зависимостях.
На Windows для обычной работы программы Docker и Linux не требуются.

## Демонстрация ошибок

По очереди меняйте один параметр в `config.yaml` и запускайте приложение:

```console
py -m src.main --show-config
```

| Изменение | Ожидаемый результат |
| --- | --- |
| `package_name: ""` | Ошибка имени пакета |
| `repository: "abc"` | Ошибка URL |
| `test_mode: "false"` | Ошибка типа режима |
| `package_version: ""` | Ошибка версии |
| `max_depth: -1` | Ошибка глубины |

После каждой проверки верните исходное значение.
Программа пишет ошибку в stderr и завершается с кодом 1.
Также обрабатываются отсутствие файла, неправильный YAML,
пропущенные и неизвестные ключи.

Для проверки ошибок второго этапа используйте запуск
`py -m src.main --direct`:

- `package_name: "no-such-package-xyz"`: пакет не найден.
- `package_version: "0.0-r0"`: версия не найдена, вывод доступных версий.
- URL несуществующего каталога в `repository`: ошибка скачивания индекса.

Также обрабатываются тайм-аут, повреждённый архив, отсутствие APKINDEX
в архиве и некорректные записи внутри него. При отсутствии зависимостей
выводится `нет`. После демонстрации верните рабочие настройки.

В тестовом режиме также проверяются синтаксис YAML, имена A-Z,
списки зависимостей, отсутствие корня и ссылок на неописанные пакеты.

## Тесты

```console
py -m unittest discover -s tests -v
```

78 тестов проверяют конфигурацию, загрузку и разбор индекса, выбор
версий, виртуальные зависимости, DFS, глубину, циклы и ошибки.
Также проверяются порядок загрузки, отсутствие дубликатов, цикл с готовым
листом и предупреждение о частичном графе. Есть цепочка из 1501 узла
для проверки отсутствия рекурсивного обхода.
Автоматические тесты используют искусственные данные и не требуют интернета.

## Устройство кода

- `src/config.py`: `read_mapping` читает YAML; `require_text` проверяет
  строки; `check_repository` проверяет URL или файл; `validate_config`
  проверяет пять параметров; `load_config` объединяет чтение и проверку.
  `Config` хранит настройки, `ConfigError` обозначает ошибку настроек.
- `src/main.py`: `parse_arguments` разбирает `--config`, `--show-config`,
  `--direct`, `--order`; `show_config` выводит настройки,
  `show_dependencies` - прямые зависимости, `show_graph` - граф,
  `show_order` - порядок загрузки; `main` управляет запуском и ошибками.
- `src/repository.py`: `index_url` строит адрес индекса, `download_index`
  скачивает архив, `unpack_index` читает его, `parse_record` и `parse_index`
  разбирают метаданные, `find_package` выбирает точную версию,
  `get_package` объединяет эти действия. `Package` хранит метаданные,
  `RepositoryError` обозначает ошибку получения данных.
- `src/graph.py`: `build_graph` строит граф стеком, `find_cycles` ищет
  обратные рёбра; `analyze_graph` выбирает `analyze_test_graph` или
  `analyze_alpine_graph`. `Graph` хранит рёбра, глубины и циклы.
- `src/test_repository.py`: `valid_name` проверяет имена A-Z,
  `load_test_repository` читает и проверяет учебный граф.
- `src/resolver.py`: `parse_dependency` разбирает ограничения,
  `package_label` создаёт метку узла, `Resolver` индексирует поставщиков
  и разрешает зависимости, `choose_candidate` выбирает пакет.
- `src/versions.py`: `version_tokens` и `compare_token` разбирают и сравнивают
  компоненты; `compare_versions` сравнивает версии, `matches_version`
  проверяет ограничение.
- `src/order.py`: `loading_order` выполняет топологическую сортировку
  зависимостей, отклоняет циклы и ссылки на неописанные узлы.
- `tests/test_config.py`: проверки корректных данных и ошибок.
- `tests/test_repository.py`: проверки второго этапа без доступа к сети.
- `tests/test_graph.py`: проверки DFS, глубины, циклов и учебных файлов.
- `tests/test_resolver.py`: проверки разрешения имён и сравнения версий.
- `tests/test_order.py`: свойства порядка загрузки и его командная строка.
- `tools/compare_apk.py`: `our_graph` строит граф, `real_apk_order` получает
  эталонный план симуляции, `explain_install_if` проверяет условия дополнений,
  `compare_order` сравнивает результаты,
  `main` запускает сравнение трёх пакетов.
- `.github/workflows/validate.yml`: автоматические тесты и сравнение с apk.
- `examples/`: пять конфигураций учебных графов.

## Сохранение этапа в Git

Локальная история начинается коммитом:
`feat(config): implement stage 1 YAML configuration`.
Второй этап сохраняется отдельным коммитом:
`feat(repository): fetch direct apk dependencies for exact version`.
Третий этап сохраняется коммитом:
`feat(graph): add iterative DFS with depth limits and test repositories`.
Четвёртый этап сохраняется коммитом:
`feat(order): add dependency loading order and real apk comparison`.

[eemp7y/apk-dependency-graph](https://github.com/eemp7y/apk-dependency-graph).
